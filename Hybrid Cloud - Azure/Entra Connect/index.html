Alternate UPN Suffix Configuration

12 steps

Before syncing anything, mtlab.local's accounts needed a usable UPN suffix — .local isn't a domain Entra ID can verify. Added mtlab.com as an alternate UPN suffix on-prem, demonstrated the change on MT.Admin through the GUI, then applied it to the remaining in-scope accounts via PowerShell.

Note RSAT (AD DS and AD LDS Tools) was already installed on SRV-ADMIN01 as part of the PAW setup — see Automation & Scripting > Setup (PAW/SRV-ADMIN01 walkthrough). This section picks up from there, using the console rather than the domain controller directly, in line with the Tier 0 PAW model.

Opening Active Directory Domains and Trusts

Launched Active Directory Domains and Trusts from SRV-ADMIN01, logged in as LAB\MT.Admin — mtlab.local visible in the tree.

2

Opening Properties on the root node

Right-clicked the root node (Active Directory Domains and Trusts) and selected Properties to reach the UPN Suffixes tab.

3

The UPN Suffixes tab, with no alternative suffixes configured yet.

4

Entering mtlab.com

Typed mtlab.com into the alternative UPN suffix field — a cleaner login suffix than the unusable .local domain.

5

mtlab.com added

Clicked Add — mtlab.com now appears in the list, available to assign to accounts domain-wide.

6

Opening Active Directory Users and Computers

Opened Active Directory Users and Computers next, to demonstrate reassigning the suffix on an actual account.

7

MT.Admin in the IT OU

Navigated to the IT OU under Corp, where MT.Admin and MT.AdminScripts live.

8

Opening MT.Admin's Properties

Right-clicked MT.Admin and selected Properties.

9

Account tab — before (@mtlab.local)

The Account tab, before the change — MT.Admin@mtlab.local.

10

Account tab — after (@mtlab.com)

Switched the suffix dropdown to @mtlab.com and applied — MT.Admin@mtlab.com.

11

Verifying with PowerShell

Get-ADUser -Identity MT.Admin -Properties UserPrincipalName confirms UserPrincipalName: MT.Admin@mtlab.com.

12

Applying the suffix to the remaining accounts

Rather than repeat the GUI steps, applied the same suffix change via Set-ADUser -Identity "<name>" -UserPrincipalName "<name>@mtlab.com" for MT.AdminScripts and MT.User, verifying each with Get-ADUser immediately after.

Constraint mtlab.com isn't a domain I actually own, so it can't be verified as a custom domain inside Entra ID — that requires proving ownership via a DNS TXT record. This on-prem suffix change is real and confirmed above, but the cloud-side verification step is a separate mechanism that this lab can't complete. The practical effect shows up later: synced accounts still resolve to the default .onmicrosoft.com UPN in the cloud, which is expected behavior given the constraint, not a bug.

Post-Install Verification

4 steps

A completed sync isn't proof the hybrid identity actually works — verified the scope on the cloud side, the sync engine's own operations log, and finished with an end-to-end sign-in test from a standard client rather than the domain controller.

1

Entra ID Users — synced accounts

Entra ID > Users confirms the on-prem accounts came across correctly — MT.Admin, MT.AdminScripts, and MT.User all show On-prem: Yes, alongside other accounts from the synced OUs. SOperations and the built-in accounts, correctly, do not appear.

2

Full user list

The rest of the list, confirming the full scope of what synced from the selected OUs.

3

Synchronization Service Manager

On SRV-ADMIN01, Synchronization Service Manager confirms the full pipeline — Full Import, Full Synchronization, and Export all show success for both the mtlab.local and Entra ID connectors, with no synchronization errors logged.

4

End-to-end sign-in test

From the Win11-Client VM — a standard client, not the domain controller — signed into myaccount.microsoft.com as MT.User using the same password set on-prem. The successful sign-in confirms Password Hash Sync is genuinely authenticating against the on-prem credential, closing the loop from Active Directory to Microsoft Entra ID.

Lesson Learned Password Hash Sync runs on its own two-minute cycle, independent of the standard 30-minute directory delta sync — a password change (like the one needed to test MT.User's login) shows up in the cloud far faster than the rest of a sync cycle would suggest.
