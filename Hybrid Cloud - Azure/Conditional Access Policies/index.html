Note Test.User was set as both the group's owner and its member. In a production tenant, ownership of a security group that gates a person's own access would normally sit with an administrator, not the account the policy is scoped to test. Left as-is here since it does not affect how Conditional Access evaluates membership, but worth calling out as a deliberate simplification rather than an oversight.

Testing CA01 in Report-Only Mode

16 steps

Verifying a Report-only policy sounds simple, sign in as the test user and check the logs, but this stretch surfaced two real gotchas along the way: a tenant-wide setting that silences Conditional Access entirely, and a sign-in log layout that separates enforced results from report-only ones. Both are documented here as they actually happened.

1

First interactive sign-in as Test.User

Opened an InPrivate window and signed in as Test.User to trigger the first evaluation of CA01.

2

Mandatory Authenticator registration

First sign-in required registering an authentication method, driven by Security defaults being active on the tenant at this point, not by CA01 which was still Report-only.

3

Checking the sign-in log

Switched to Monitoring & health > Sign-in logs, User sign-ins (interactive) tab, to review the Test.User event against OfficeHome.

4

Basic info: single-factor authentication

Basic info showed Single-factor authentication, Status Success, with a note that MFA was satisfied by a claim already present in the token from the registration step.

5

Conditional access tab shows Security Defaults, not CA01

The Conditional access tab lists only Security Defaults, not CA01. Security defaults and Conditional Access are mutually exclusive, so with defaults on, CA01 was never being evaluated at all.

6

Confirming Security defaults is enabled

Confirmed in Entra ID > Overview > Properties that the tenant is protected by Security defaults.

7

Opening the Security defaults panel

Opened Manage security defaults, currently set to Enabled.

8

Disabling Security defaults

Switched the setting to Disabled, selecting "My organization is planning to use Conditional Access" as the reason, and saved.

9

Signing in again post-disable

Opened a fresh InPrivate window and signed in as Test.User again, now that Security defaults was out of the way.

10

Sign-in succeeds with no MFA prompt

Sign-in completed with no MFA prompt, exactly as expected for a Report-only policy, which evaluates but never enforces.

11

Reviewing the new sign-in event

Back in Sign-in logs, the newest Test.User event was ready to inspect.

12

Conditional access tab shows Not applicable

The main Conditional access tab reads Not applicable. This tab only lists what was actually enforced, and Report-only policies never enforce anything, so this looked like a failure at first.

13

Finding CA01 under the Report only tab

A separate Report only tab lists CA01 with Grant control Mfa, confirming the policy matched and evaluated exactly as intended.

14

Policy list still shows Report-only

Confirmed CA01's State is still Report-only in the policy list before making any changes.

15

Policy details panel

The Policy details view lays out CA01's full configuration in one place, 1 group included, 1 user excluded, all resources, MFA required, state Report-only.

16

Opening the policy to flip the toggle

With Report-only confirmed working correctly, opened CA01's edit screen ready to move Enable policy to On.

Constraint Security defaults and Conditional Access cannot run at the same time. With Security defaults enabled, CA01 evaluated silently in the background but never appeared as the matching policy in the sign-in log, Security Defaults did instead. Security defaults has to be disabled before a Conditional Access policy's Report-only or enforced results become visible.
Lesson Learned The sign-in log's Conditional access tab only shows policies that actually enforced. A policy running in Report-only never shows up there, it lives under a separate Report only tab instead. Seeing Not applicable on the main tab does not mean a Report-only policy failed to evaluate, it means the Report only tab is the one to check.

Building and Enabling CA02: Block Legacy Authentication

13 steps

With CA01 proven end to end, built a second policy targeting legacy authentication protocols, the ones that predate modern auth and cannot satisfy MFA or Conditional Access at all. Same test group, same Report-only discipline before enforcing.

1

Clean baseline before CA02

Confirmed CA01 alone, State On, before starting the second policy.

2

Naming CA02

Named the new policy CA02 - Block Legacy Authentication.

3

Selecting users and groups

Same as CA01, chose Select users and groups, unconfigured until a group is picked.

4

Reusing CA-MFA-Test

Reused CA-MFA-Test rather than scoping to All users, keeping a potentially disruptive block policy contained to the test account.

5

Target resources: All resources

Selected All resources under Target resources, same as CA01.

6

Opening Conditions

Scrolled to Conditions, the section this policy actually depends on, since legacy auth is defined by client app type rather than group or resource.

7

Client apps panel, unconfigured

Opened Client apps under Conditions, defaulted to Configure: No.

8

Scoping to legacy authentication clients

Set Configure to Yes and checked only Exchange ActiveSync clients and Other clients under Legacy authentication clients, leaving Browser and Mobile apps and desktop clients unchecked. This is the step most likely to get missed, checking a modern auth box here would defeat the point of the policy.

9

Setting Grant to Block access

Under Grant, selected Block access rather than Grant access, since the goal here is to deny legacy auth outright rather than layer a control on top of it.

10

Final review before creating CA02

With Grant, Target resources, and Conditions all configured and Enable policy left on Report-only, clicked Create.

11

CA02 created alongside CA01

The policy list now shows both policies, CA01 On and CA02 Report-only.

12

Enabling CA02

Moved CA02's Enable policy to On and saved.

13

Both policies enforcing

The final state of this lab: CA01 and CA02 both showing State: On, a group scoped MFA requirement and a legacy authentication block, both fully enforcing.

Note Testing CA02 against a live legacy auth connection was attempted using PowerShell with basic authentication against Exchange Online, and it failed immediately with a WinRM transport error rather than an authentication denial. That failure turned out to have nothing to do with CA02, Microsoft fully retired Remote PowerShell basic-auth connections to Exchange Online tenant-wide back in October 2022, independent of any Conditional Access configuration. Rather than chase an increasingly rare legacy client just to force a green result, CA02 was enabled as-is. It serves as defense-in-depth against a protocol surface Microsoft has already been closing off at the platform level, and that finding is itself a more accurate picture of the current state of legacy authentication than a manufactured test would have been.
