FortiGate 60E Firewall Setup & Config

Replacing a virtualized pfSense firewall with a physical FortiGate 60E as the lab's perimeter firewall — dedicated WAN/LAN interfaces, a routed transit subnet to the core switch, firewall policy, static routing, and a management VLAN migration.

Overview

The FortiGate 60E was introduced as a replacement for pfSense, which had persistent connectivity issues stemming from a fundamental architectural limitation. The FortiGate 60E is a physical enterprise-grade next-generation firewall manufactured by Fortinet, providing dedicated WAN and LAN interfaces, hardware-accelerated packet processing, and FortiOS — the same operating system used in production enterprise and MSP environments.

pfSense — Initial Implementation and Limitations

pfSense was initially deployed as a virtualized firewall running on the Hyper-V host (SRV-HYPERV-01). While pfSense is a capable open-source firewall platform, its integration into this lab environment exposed a critical architectural constraint.

The pfSense LAN interface relied on a USB network adapter connected to the 2950 Fa0/2 port on VLAN 20. This meant the same physical USB adapter was carrying both pfSense LAN traffic and VM traffic from the Hyper-V host, with no dedicated physical separation between the firewall and the network it was protecting. This created persistent connectivity issues that could not be resolved without additional hardware.

The decision was made to replace pfSense with a physical FortiGate 60E, eliminating the shared adapter problem entirely and introducing enterprise-grade firewall hardware directly relevant to the target employer environment.

Physical Integration

The FortiGate 60E was physically integrated into the existing lab network as the perimeter firewall:

  • WAN1 connected to the SOHO router (DHCP, 192.168.1.148)
  • Internal LAN port 1 connected to 3550 Fa0/24 via transit subnet 192.168.100.0/30

All internet-bound traffic from the lab now flows through the FortiGate before reaching the SOHO router, providing NAT, stateful packet inspection, and firewall policy enforcement.

Initial Access

The FortiGate 60E was configured entirely via serial console using PuTTY on COM6, as the WebGUI was inaccessible prior to initial configuration. This is standard procedure for first-time FortiGate deployment. Initial login used the default admin credentials via the serial console connection.

Initial LAN Interface Configuration — Troubleshooting

After completing WAN1 configuration, the next step was assigning the LAN-side IP address (192.168.50.1/24) to the FortiGate's internal interface. Initial attempts to configure this via edit internal1 returned a command parse error before 'ip' and Command fail. Return code -61.

Investigation revealed that on the FortiGate 60E, internal1 through internal7 are physical member ports of a virtual switch — they are Layer 2 ports and cannot be assigned IP addresses directly. The routable interface is the parent virtual switch interface, internal.

Reconfiguring via edit internal with set ip 192.168.50.1 255.255.255.0 and set allowaccess http https ping ssh applied successfully, as confirmed by show system interface.

Transit Subnet Architecture

Rather than placing the FortiGate directly on an existing VLAN subnet, a dedicated /30 transit subnet (192.168.100.0/30) was established between the FortiGate and the 3550. This follows enterprise best practices by creating a clean point-to-point routed link between the firewall and the core switch, keeping the perimeter firewall logically separate from internal VLAN segments.

  • FortiGate internal interface: 192.168.100.1/30
  • 3550 Fa0/24: 192.168.100.2/30

3550 Fa0/24 Reconfiguration — Uplink to FortiGate

After successfully configuring the FortiGate's internal interface at 192.168.50.1/24, attempting to access the FortiGate WebGUI from the Hyper-V host at https://192.168.50.1 failed. The Hyper-V host was able to ping the FortiGate's WAN1 address (192.168.1.148) via the SOHO network, but could not reach 192.168.50.1 at all.

Investigation revealed the root cause — the 192.168.50.0/24 subnet had never existed as a routed segment in the lab. Previously, 192.168.50.1 was pfSense's LAN address, which was connected directly via USB adapter and never integrated into the 3550's routing table. The FortiGate was now assigned that address but no path existed for lab devices to reach it.

show interface fa0/24 on the 3550 confirmed the port still had its old configuration — a routed port with IP 192.168.1.2/24 and description "Uplink-to-SOHO-Router" — left over from when the 3550 connected directly to the SOHO router before the FortiGate was introduced.

The fix was to reconfigure Fa0/24 as the dedicated uplink to the FortiGate on the 192.168.100.0/30 transit subnet, assign it 192.168.100.2/30, and update the 3550's default route to point to the FortiGate at 192.168.100.1 rather than the SOHO router at 192.168.1.1.

Firewall Policies

Two firewall policies were configured on the FortiGate:

  • LAN-to-WAN: allows all internal traffic to reach the internet with NAT enabled
  • LAN-to-LAN: allows inter-VLAN traffic to flow between internal segments

Static Routes

Static routes were added to the FortiGate so return traffic destined for internal VLANs is correctly forwarded back through the 3550:

  • 192.168.10.0/24 via 192.168.100.2 (VLAN 10 — Servers)
  • 192.168.20.0/24 via 192.168.100.2 (VLAN 20 — Infrastructure)
  • 192.168.40.0/24 via 192.168.100.2 (VLAN 40 — Clients)
  • 192.168.50.0/24 via 192.168.100.2 (VLAN 50 — Management)

Management VLAN Migration — VLAN 1 to VLAN 50

During connectivity verification, ping tests from the FortiGate to the switch management IPs (192.168.50.2, 192.168.50.4) failed. Investigation revealed that while the switches had management IPs assigned on the 192.168.50.0/24 subnet, they were configured on VLAN 1 rather than a dedicated management VLAN.

In enterprise environments, using VLAN 1 for management traffic is considered a security risk. VLAN 1 is the default VLAN on Cisco switches and is present on all ports by default, making it more susceptible to VLAN hopping attacks. Best practice is to configure a dedicated management VLAN and disable VLAN 1 where possible.

To align with enterprise security standards, VLAN 50 was created as a dedicated management VLAN on both switches. Switch management IPs were migrated from VLAN 1 SVIs to VLAN 50 SVIs, and VLAN 50 was added to the trunk allowed list on both the 3550 and 2950.

  • 3550 (Switch002) VLAN 50 SVI: 192.168.50.6/24
  • 2950 (Switch001) VLAN 50 SVI: 192.168.50.2/24

Connectivity Verification

End-to-end connectivity was verified across all VLANs following the completion of all configurations:

  • FortiGate to internet (8.8.8.8): Success
  • FortiGate to all internal VLANs: Success
  • FortiGate to management IPs (192.168.50.2, 192.168.50.6): Success
  • Windows Server DC to internet: Success
  • Windows Server DC to VLAN 10 devices: Success
  • Raspberry Pi 5 to other VLANs and internet: Success

Note: the Hyper-V host (192.168.20.11) does not respond to inbound ping requests from other devices due to Windows Firewall blocking inbound ICMP by default. This is expected behavior and confirmed correct security posture — the Hyper-V host can successfully initiate outbound connections to all VLANs and the internet.
