Windows Server 2022: AD DS Installation & Active Directory Setup

Standing up Active Directory Domain Services and building out the mtlab.local domain environment on DC01.

Domain: mtlab.local· Domain Controller: DC01.mtlab.local· Host: SRV-HYPER-01

Overview

With the Hyper-V host configured and the Windows Server 2022 virtual machine deployed on SRV-HYPER-01, the next step in the lab build was to stand up Active Directory Domain Services (AD DS) and promote the server to a domain controller. This document covers the full process: installing the AD DS role through Server Manager, running the AD DS Configuration Wizard to promote the VM to a domain controller for a new forest, and then building out the initial Active Directory environment with an organizational unit structure, user accounts, and basic account security hardening.

The domain established for the lab is mtlab.local, with DC01.mtlab.local serving as the primary domain controller at IP address 192.168.20.10. All work documented here was performed inside the Windows Server 2022 VM running on the Hyper-V host.

Part 1: AD DS Role Installation

Before the server can be promoted to a domain controller, the Active Directory Domain Services role must be installed. This is done through the Add Roles and Features Wizard in Server Manager.

Launching the Wizard

From the Server Manager Dashboard, the Add Roles and Features Wizard was launched. The destination server shown at this stage is DC01.mtlab.local at 192.168.20.10, running Windows Server 2022 Standard Evaluation.

Installation Type

Role-based or feature-based installation was selected, which configures a single server by adding roles, role services, and features.

Server Selection

DC01.mtlab.local was selected from the server pool as the destination server for the role installation.

Selecting the AD DS Role

On the Server Roles page, Active Directory Domain Services was selected from the roles list.

Selecting AD DS triggered a pop-up prompting to add required management features:

  • Group Policy Management
  • Remote Server Administration Tools → Role Administration Tools → AD DS and AD LDS Tools → AD DS Tools
  • Active Directory Administrative Center
  • AD DS Snap-Ins and Command-Line Tools

Add Features was clicked to include all required dependencies.

Features

On the Features page, Azure Arc Setup and Group Policy Management were checked. All other features were left at their defaults.

AD DS Information Page

The wizard presented an informational page summarizing what AD DS is and noting key requirements: the need for a DNS server on the network, and the recommendation to have a minimum of two domain controllers for redundancy in a production environment. For this lab environment, a single DC is sufficient.

Confirmation and Installation

The Confirm Installation Selections page showed the full list of roles and features to be installed. Auto-restart was initially unchecked.

The auto-restart option was then enabled. A confirmation dialog appeared warning that the server would restart automatically without additional notification if required. Yes was clicked to allow automatic restarts.

Installation was started. The progress bar advanced through the role installation.

Installation completed successfully. The Results page showed the message: Configuration required. Installation succeeded on DC01.mtlab.local. A prompt to promote this server to a domain controller appeared as a next step.

Part 2: Domain Controller Promotion

With the AD DS role installed, the server needed to be promoted to a domain controller. Installing the role alone does not create a domain or promote the server: that requires running the AD DS Configuration Wizard separately. The post-install notification in Server Manager flagged this with a post-deployment configuration alert.

Post-Deployment Notification

After the role installation completed, Server Manager displayed a post-deployment configuration alert under the flag icon: Configuration required for Active Directory Domain Services at DC01. The Promote this server to a domain controller link was clicked to launch the AD DS Configuration Wizard.

Deployment Configuration: Adding a New Forest

The AD DS Configuration Wizard opened to the Deployment Configuration page. The default selection of Add a domain controller to an existing domain was shown first, but since this is a new lab environment with no existing domain, Add a new forest was selected instead.

With Add a new forest selected, the Root domain name field was filled in as mtlab.local.

Domain Controller Options

The Domain Controller Options page was configured with the following settings:

Forest Functional LevelWindows Server 2016
Domain Functional LevelWindows Server 2016
DNS ServerChecked
Global Catalog (GC)Checked
Read Only DC (RODC)Unchecked

The Directory Services Restore Mode (DSRM) password was set on this page. This password is used to access the server in Directory Services Restore Mode for AD recovery purposes and is separate from the domain Administrator password.

DNS Options

Note: The DNS Options page displayed a warning banner: a delegation for this DNS server cannot be created because the authoritative parent zone cannot be found. This is expected behavior in a standalone lab environment — there is no parent DNS infrastructure for mtlab.local to delegate from, so the warning is informational only and requires no action.

Create DNS delegation was left unchecked.

Additional Options: NetBIOS Name

The Additional Options page auto-populated the NetBIOS domain name as LAB, derived from the first segment of the mtlab.local domain name. This is the short name used for pre-Windows 2000 style logons in the format LAB\username.

Paths

The Paths page showed the default storage locations for the AD DS database, log files, and SYSVOL folder. All defaults were kept.

Database folderC:\Windows\NTDS
Log files folderC:\Windows\NTDS
SYSVOL folderC:\Windows\SYSVOL

Review Options

The Review Options page summarized the full configuration before installation:

  • Configure this server as the first Active Directory domain controller in a new forest
  • New domain name: mtlab.local (also the name of the new forest)
  • NetBIOS name: LAB
  • Forest Functional Level: Windows Server 2016
  • Domain Functional Level: Windows Server 2016
  • Global Catalog: Yes
  • DNS Server: Yes
  • Create DNS Delegation: No

Prerequisites Check

The Prerequisites Check ran to validate the configuration before promotion. After a brief verification period, all prerequisite checks passed successfully.

Two warnings were present in the results, both expected and non-blocking:

  • Windows Server 2022 domain controllers have a default security setting that prevents weaker cryptography algorithms compatible with Windows NT 4.0. This is a default hardening setting and does not affect the lab.
  • A delegation for this DNS server cannot be created because the authoritative parent zone cannot be found — the same message as the DNS Options page, expected in a standalone lab with no parent DNS zone.

Installation and Reboot

Install was clicked to begin the DC promotion. The Installation page showed progress starting, then moved to configuring the DNS Server service as promotion proceeded.

The Results page showed a green success banner: This server was successfully configured as a domain controller. Immediately after, a "You're about to be signed out" overlay appeared, indicating the server was restarting to complete the promotion.

The VM restarted, applying computer settings during the boot process.

After the reboot, the login screen confirmed the domain promotion was complete. The login now showed LAB\Administrator rather than the local Administrator account, confirming the server was operating as the domain controller for the LAB domain.

Part 3: Active Directory Environment Setup

With the domain controller up and the domain live, the next step was to build out the initial Active Directory environment. This included opening Active Directory Users and Computers, creating an organizational unit structure to represent a corporate environment, creating user accounts, and hardening the default built-in accounts.

Opening Active Directory Users and Computers

Active Directory Users and Computers (ADUC) was accessed from Server Manager via Tools > Active Directory Users and Computers. At this stage, Server Manager showed four installed roles: AD DS, DHCP, DNS, and File and Storage Services.

ADUC opened with the default domain structure for mtlab.local. The left pane showed the standard default containers created during domain promotion:

  • Builtin — built-in domain local security groups
  • Computers — default container for computer objects
  • Domain Controllers — organizational unit for DC objects
  • ForeignSecurityPrincipals — security principals from trusted external domains
  • Managed Service Accounts — managed service account objects
  • Users — default container for users and domain-level security groups

Creating the Corp Organizational Unit

Rather than placing user and group objects in the default Users container, a dedicated organizational unit structure was created to simulate a more realistic corporate environment and to demonstrate proper AD organization.

The Corp OU was created at the domain root level by right-clicking mtlab.local, selecting New > Organizational Unit, and entering Corp as the name. The Protect container from accidental deletion option was left checked.

Creating Sub-OUs Inside Corp

With the Corp OU in place, department-level sub-OUs were created inside it to represent different functional areas of the simulated organization. Each was created by right-clicking Corp > New > Organizational Unit.

The following sub-OUs were created under Corp:

  • Users — for standard domain user accounts
  • Engineering — for engineering department users and resources
  • HR — for human resources
  • IT — for IT department accounts
  • Sales — for sales department users

Creating User Accounts

MT.Admin — Domain Admin Account

A dedicated domain admin account was created to avoid using the built-in Administrator account for day-to-day administration. This follows the principle of least privilege at the admin level: the built-in Administrator is disabled, and a named admin account is used instead, making administrative actions attributable and auditable.

MT.Admin was added to the Domain Admins security group to grant full domain administrative privileges.

MT.Admin was also added to the Protected Users security group. Protected Users is a special security group in Windows Server 2012 R2 and later that applies additional authentication protections: it prevents the use of weaker authentication protocols such as NTLM, DES, and RC4, and limits credential caching. Adding privileged accounts to Protected Users is a security hardening best practice.

Reviewing the Built-in Groups Structure

With the Corp OU structure and user accounts in place, the default Users container and Builtin container were reviewed to understand the existing domain group landscape.

Users Container

The default Users container holds the domain-level security groups and the built-in Administrator and Guest accounts. Key groups visible include:

  • Domain Admins — designated administrators of the domain
  • Domain Users — all domain users (every user account is a member by default)
  • Domain Computers — all workstations and servers joined to the domain
  • Enterprise Admins — administrators of the entire Active Directory forest
  • Schema Admins — accounts that can modify the AD schema
  • Group Policy Creator Owners — accounts that can modify Group Policy for the domain
  • Protected Users — accounts with additional authentication protections

Builtin Container

The Builtin container holds domain local security groups that are built into the operating system. These groups define local server-level permissions and include groups such as:

  • Administrators — full administrative access to the domain controllers
  • Backup Operators — permission to back up and restore files regardless of permissions
  • Remote Desktop Users — members can log on remotely via RDP
  • Remote Management Users — members can access WMI resources remotely
  • Event Log Readers — members can read event logs
  • Server Operators — members can administer domain servers
  • Print Operators — members can manage printers

Hardening Built-in Accounts

As a security baseline, both of the built-in accounts in the domain were disabled. These accounts represent well-known targets and should not be left active in any environment, lab or production.

Disabling the Built-in Administrator Account

The built-in Administrator account in the Users container was disabled. With MT.Admin in place as a named domain admin account with a known password and audit trail, the built-in Administrator account serves no operational purpose and represents an unnecessary attack surface.

The account was disabled by right-clicking Administrator > Disable Account.

Guest Account: Already Disabled

The Guest account was reviewed and confirmed to already be in a disabled state. The context menu showed Enable Account as the available action, confirming it was disabled by default and no further action was required.

Summary

This document covered the full process of installing the AD DS role, promoting the Windows Server 2022 VM to a domain controller for the mtlab.local forest, and building the initial Active Directory environment.

The following was completed:

  • Installed the Active Directory Domain Services role via Server Manager, including Group Policy Management and all required RSAT tools
  • Promoted DC01.mtlab.local as the first domain controller in a new forest, establishing the mtlab.local domain with NetBIOS name LAB
  • Configured forest and domain functional levels at Windows Server 2016
  • Verified DC promotion with a successful post-reboot domain login as LAB\Administrator
  • Opened ADUC and reviewed the default domain container structure
  • Created the Corp organizational unit at the domain root, with sub-OUs for Users, Engineering, HR, IT, and Sales
  • Created user accounts: MT.User (standard user in Corp\Users), Security Operations (dept user in Corp\Engineering), and MT.Admin (domain admin)
  • Added MT.Admin to Domain Admins and Protected Users security groups
  • Disabled the built-in Administrator account and confirmed the Guest account was already disabled

The Active Directory environment is now operational and ready for further configuration including Group Policy, DHCP scope management, DNS review, and additional user and group provisioning.
