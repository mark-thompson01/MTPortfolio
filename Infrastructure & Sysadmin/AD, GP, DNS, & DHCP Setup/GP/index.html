Group Policy Administration

Five day-to-day Group Policy demonstrations configured and verified in the mtlab.local domain.

Domain: mtlab.local· Domain Controller: DC01· OS: Windows Server 2022

Overview

Group Policy is one of the most powerful administrative tools in a Windows domain environment. It allows a systems administrator to enforce settings, restrictions, and behaviors across users and computers from a central management console: the Group Policy Management Console (GPMC).

With that power comes an important lesson learned hands-on in this lab: Group Policy should be applied carefully, deliberately, and with a clear understanding of scope. Overly broad GPO links, misconfigured settings, or policies applied without proper security filtering can quickly cascade into unintended consequences across the domain. In this lab, that became evident when a Control Panel restriction initially blocked access for both standard users and administrative accounts, including access to Credential Manager, which in turn disrupted the mapped drive configuration workflow.

This document covers five fundamental Group Policy demonstrations configured in the mtlab.local domain, each representing day-to-day administrative use of Group Policy in a real-world environment. These demonstrations are intentionally administrative and operational in nature, distinct from the security-hardening GPO configurations covered separately in the AD Security Hardening lab.

Demonstrations Covered

  • Logon Banner (Workstation-Logon-Banner GPO)
  • Account Lockout Policy (Default Domain Policy)
  • Restrict Control Panel for Standard Users (Corp-Users-Restrictions GPO)
  • Block Removable Storage, USB Lockdown (Corp-Workstation-Policy GPO)
  • Mapped Network Drive via GPO Preferences (Corp-Drive-Mapping GPO)

1. Logon Banner

GPO: Workstation-Logon-Banner

A logon banner is a standard administrative control used across enterprise environments to display a legal notice or usage policy before a user is permitted to log in. In this demonstration, a dedicated GPO is created and configured to display an "Authorized Use Only" message on the Windows 11 domain-joined client at the login screen.

Group Policy Management is accessed from Server Manager under Tools.

With Group Policy Management open, right-clicking the domain (mtlab.local) presents the option to create a new GPO and link it here. This is where the Workstation-Logon-Banner GPO originates.

The New GPO dialog is used to name the policy. The name Workstation-Logon-Banner is entered and the GPO is created.

The GPMC tree now shows the Workstation-Logon-Banner GPO linked at the domain level, visible alongside the Default Domain Policy.

Right-clicking the GPO presents the context menu. Selecting Edit opens the Group Policy Management Editor for this policy.

The Group Policy Management Editor opens for the Workstation-Logon-Banner policy, showing the Computer Configuration and User Configuration hierarchy.

Navigating to Computer Configuration, Policies, Windows Settings, Security Settings, Local Policies, Security Options reveals the full list of security option policies. The two Interactive logon settings are located here: Message title for users attempting to log on and Message text for users attempting to log on.

Double-clicking the Message title setting opens its properties dialog. Define this policy setting is checked to activate it.

The title text "Authorized Use Only" is entered in the field below the checkbox.

Back in the Security Options list, the Message title now shows "Authorized Use Only" in the Policy Setting column. The Message text setting is highlighted next for configuration.

The Message text properties dialog is opened and the banner message is entered: "This system is for authorized users only. Unauthorized access is prohibited."

Both settings are now configured. The Security Options list confirms the Message text truncated preview and the Message title set to "Authorized Use Only."

Client-Side Verification

With the GPO configured, gpupdate /force is run on the Windows 11 client to immediately pull the updated policy from the domain controller rather than waiting for the background refresh interval.

After signing out, the logon banner appears on the Windows 11 client login screen before the user is permitted to authenticate. The banner displays the configured title "Authorized Use Only" and the accompanying message text, confirming the GPO applied successfully.

2. Account Lockout Policy

GPO: Default Domain Policy

Account lockout policy is a foundational domain security control that limits how many consecutive failed login attempts an account can accumulate before being temporarily locked. This protects domain accounts against brute-force and password-spraying attacks by enforcing an automatic lockout after a defined threshold.

Note: Account lockout policy must be configured at the domain level within the Default Domain Policy to apply to all domain accounts. Configuring it inside any other GPO or at an OU level will not affect domain accounts.

The Default Domain Policy is selected in the GPMC and its Scope tab is reviewed. The policy is linked to mtlab.local and applies to Authenticated Users, confirming domain-wide scope.

The Default Domain Policy is opened for editing. The Group Policy Management Editor opens showing the Computer Configuration and User Configuration trees.

Navigating to Computer Configuration, Policies, Windows Settings, Security Settings, Account Policies, reveals the Account Lockout Policy node alongside Password Policy and Kerberos Policy.

Clicking Account Lockout Policy displays the four configurable settings. All are initially at their default states: Account lockout threshold at 0 (disabled), duration and reset counter not defined.

Double-clicking Account lockout threshold opens its properties. The value is set to 5 invalid logon attempts, meaning an account will lock after 5 consecutive authentication failures.

After setting the threshold, Windows automatically suggests values for the duration and reset counter. The Account lockout duration properties dialog is opened and set to 30 minutes, meaning a locked account automatically unlocks after 30 minutes.

The Reset account lockout counter after properties dialog is opened and set to 15 minutes. This means the failed attempt counter resets back to zero after 15 minutes of no failed attempts.

The Account Lockout Policy view now confirms all three values are configured: Account lockout duration at 30 minutes, Account lockout threshold at 5 invalid logon attempts, and Reset account lockout counter after at 15 minutes.

Note on FGPP: After configuring the domain-wide Account Lockout Policy, the MT.Admin account began receiving password expiration prompts at an unexpected interval. This was traced to the FGPP-DomainAdmins Fine-Grained Password Policy (PSO) configured in a previous lab, which had the Enforce maximum password age option checked and set to 42 days, matching the domain-wide password policy. Since MT.Admin is a member of Domain Admins, the FGPP was applying that expiration to it. The fix was to open Active Directory Administrative Center, navigate to the Password Settings Container, open FGPP-DomainAdmins, and uncheck Enforce maximum password age. Fine-Grained Password Policies allow different password controls to be applied per group, so administrative accounts can have different settings than standard domain users without one policy compromising the other.

3. Restrict Control Panel for Standard Users

GPO: Corp-Users-Restrictions

Restricting access to Control Panel and PC Settings for standard user accounts is a common administrative control in managed environments. It prevents standard users from modifying system settings, changing network configurations, or accessing sensitive areas of the operating system that are outside the scope of their role.

This demonstration also illustrates one of the most important lessons in Group Policy administration: the scope of a GPO must be deliberately controlled. An overly broad link combined with the default Authenticated Users security filtering caused this policy to apply to the MT.Admin account as well, blocking access to Credential Manager during the mapped drive configuration. The resolution involved configuring security filtering to scope the policy precisely to MT.User only.

Creating and Configuring the GPO

Right-clicking the domain in GPMC opens the context menu to create a new GPO. The New GPO dialog is used to name the policy Corp-Users-Restrictions.

Right-clicking the Corp-Users-Restrictions GPO opens the context menu. Edit is selected to open the Group Policy Management Editor.

Navigating to User Configuration, Policies, Administrative Templates, Control Panel reveals the available Control Panel policy settings. "Prohibit access to Control Panel and PC settings" is selected. The policy properties dialog opens in its default Not Configured state, then is switched to Enabled. This prevents Control Panel and PC Settings from launching on machines where the policy applies to the logged-in user.

Client-Side Verification

gpupdate /force is run on the Windows 11 client to immediately apply the updated policy. On the Windows 11 client, attempting to open Control Panel while logged in as MT.User triggers the restriction message: "This operation has been cancelled due to restrictions in effect on this computer. Please contact your system administrator." This confirms the GPO applied and is actively blocking Control Panel access.

Troubleshooting: Unintended Scope and Security Filtering

After configuring the restriction, it became clear the policy was also affecting the MT.Admin account, blocking access to Control Panel and Credential Manager on the Windows 11 client. The root cause was that the GPO was linked at the domain root and applied to Authenticated Users by default, meaning it reached every authenticated account in the domain, not just standard users.

The resolution was to use security filtering to scope the GPO precisely to MT.User only.

The Corp-Users-Restrictions GPO is selected in GPMC. The Scope tab shows the current state: the GPO is linked to mtlab.local and Security Filtering shows Authenticated Users, which is why it applied broadly.

Clicking Remove on the Authenticated Users entry triggers a confirmation prompt.

A second prompt appears warning that removing Authenticated Users may prevent computers from reading the GPO data. This is an important warning: computer accounts still need read permission on the GPO for User Configuration settings to process correctly. For this lab the warning is acknowledged and the removal proceeds, with MT.User being added as the precise target.

The Select User, Computer, or Group dialog is used to add MT.User to Security Filtering, with the object name entered.

gpupdate /force is run on the client to apply the corrected security filtering.

After gpupdate /force on the client, MT.Admin is now able to open Control Panel successfully, confirming the security filter is working correctly. MT.User still receives the restriction message when attempting to open Control Panel, confirming the policy continues to apply correctly to the intended account.

Closing screenshots confirming MT.Admin's restored Control Panel access and MT.User's continued restriction are still to be added.
Key lesson: Group Policy scope must be intentional. The default Authenticated Users security filtering means a GPO linked at the domain root will reach every account in the domain. Security filtering is the mechanism for scoping a policy precisely to the intended principals. In production environments, this distinction matters significantly: misscoped policies can disrupt administrative accounts, service accounts, or entire OUs. Always verify the intended scope before linking a GPO, and use security filtering or OU-level linking rather than domain-root links for policies that target specific groups of users or computers.

4. Block Removable Storage (USB Lockdown)

GPO: Corp-Workstation-Policy

Blocking removable storage is a standard data loss prevention control in managed environments. By denying access to all removable storage classes via Group Policy, an administrator can prevent users from copying sensitive data to USB drives or introducing unauthorized media into the environment.

This setting is configured under Computer Configuration, meaning it applies to the machine rather than the user. Any user who logs into a workstation where this policy applies will be subject to the restriction regardless of their account.

Right-clicking the domain in GPMC opens the context menu to create a new GPO.

The New GPO dialog is used to name the policy Corp-Workstation-Policy.

The GPMC tree now shows Corp-Workstation-Policy alongside the other configured GPOs, confirming it was created successfully.

Right-clicking Corp-Workstation-Policy opens the context menu. Edit is selected to open the Group Policy Management Editor.

Navigating to Computer Configuration, Policies, Administrative Templates, System reveals the System subfolder list. Removable Storage Access is located in this list.

The Removable Storage Access node is selected, revealing the full list of removable storage policy settings. The setting "All Removable Storage classes: Deny all access" is visible in the list alongside more granular per-class settings.

Hovering over the setting shows the description panel explaining what the setting controls.

Double-clicking the setting opens its properties dialog. The setting is switched to Enabled, denying access to removable storage devices on machines where this policy applies.

Note: USB lockdown was configured at the GPO level in this demonstration. A client-side verification screenshot showing a USB being blocked was not captured, as the configuration itself is the primary demonstration. In a production environment, verification would be confirmed by attempting to access a USB drive on a policy-applied workstation and observing the access denied result.

5. Mapped Network Drive via GPO Preferences

GPO: Corp-Drive-Mapping

Mapping network drives via Group Policy Preferences is a common sysadmin task in domain environments. Rather than requiring users to manually map drives or running logon scripts on every machine, GPO Preferences allow the drive mapping to be defined centrally and delivered automatically at logon.

In this demonstration, a shared folder on the Raspberry Pi 3 Samba NAS (192.168.10.20) is mapped as the S: drive for domain users. Because the Raspberry Pi is not domain-joined, it authenticates separately from the domain using a local Samba user account, which introduced additional steps that reflect a realistic real-world scenario involving non-domain file shares.

Creating the GPO

Right-clicking the domain in GPMC opens the context menu to create the Corp-Drive-Mapping GPO.

The New GPO dialog names the policy Corp-Drive-Mapping.

The Corp OU is right-clicked to link the Corp-Drive-Mapping GPO to it, scoping the drive mapping to users and computers within the Corp organizational unit.

The Select GPO dialog shows all available GPOs. Corp-Drive-Mapping is selected for linking.

The Corp OU now shows Corp-Drive-Mapping linked with Link Order 1, confirming it is the first policy applied at this OU level.

Right-clicking Corp-Drive-Mapping opens the context menu. Edit is selected to open the Group Policy Management Editor.

Configuring the Drive Map Preference

In the Group Policy Management Editor, navigating to User Configuration, Preferences, Windows Settings, Drive Maps reveals the Drive Maps node. There are no items configured yet.

Using the Action menu, New, Mapped Drive creates a new drive map preference item.

The New Drive Properties dialog is configured: Action set to Create, Location set to the Samba NAS share path, Reconnect checked, Label set to Shared, and the drive letter assigned to S:.

The Common tab of the drive map preference item shows "Run in logged-on user's security context" is checked. This is required for the preference to process in the correct user session context, which is particularly important when mapping to non-domain shares where the credentials must match the logged-in user context.

Troubleshooting: Non-Domain Share Authentication and UAC Session Isolation

After configuring the GPO Preference, the S: drive did not appear in File Explorer on the Windows 11 client even after gpupdate /force and a reboot. The GPO was confirmed applied via gpresult /r, ruling out a delivery problem. The issue was specific to how Windows handles authentication to non-domain SMB shares combined with UAC session isolation.

Because the Raspberry Pi is not domain-joined, Windows cannot authenticate to its Samba share using domain credentials. A separate set of credentials (the local pi Samba account) must be provided. Additionally, drive mappings created in an elevated session do not appear in File Explorer running in a standard user context due to UAC session isolation: elevated and non-elevated processes run in different security contexts and do not share drive mappings.

The resolution was to store the Pi credentials in Windows Credential Manager under MT.Admin (once Control Panel access was restored via security filtering), and then map the drive using net use in a non-elevated Command Prompt running as MT.User.

Credential Manager is accessed from Control Panel to store the Raspberry Pi credentials.

The Add a Windows credential dialog is completed with the network address 192.168.10.20, username pi, and the Samba password. These stored credentials allow Windows to authenticate automatically to the Pi share.

The net use command is run in a non-elevated Command Prompt as MT.User to map the drive in the correct security context:

net use S: \\192.168.10.20\NAS /user:pi /persistent:yes

After running the command in the correct context, File Explorer on the Windows 11 client shows the S: drive mapped to NAS (\\192.168.10.20) under Network locations, displaying available storage. This confirms the share is accessible.

After a reboot, the S: drive mapping persists and is still visible under Network locations in This PC, confirming the /persistent:yes flag held the mapping across the session.

Key lesson: GPO Preferences drive maps work well for domain-joined file shares. When mapping to non-domain shares such as a Samba NAS, two factors must be accounted for: the credentials must be stored in Windows Credential Manager for the target user session, and the net use command must be executed in the same non-elevated user context that File Explorer runs in. Attempting to map a drive in an elevated session will not make it visible in a standard user File Explorer window. In production environments, this scenario is common when mapping drives to Linux-based NAS devices or third-party file servers that are not integrated with Active Directory.

Summary

This lab demonstrated five Group Policy configurations representing common administrative use cases in a Windows domain environment. Each GPO was created, configured, linked, and verified against a domain-joined Windows 11 client running in the mtlab.local lab environment.

The troubleshooting encountered across this lab, particularly the security filtering issue with the Control Panel restriction and the non-domain authentication challenge with the mapped drive, reflects the real-world complexity of Group Policy administration. These are not edge cases: they are the kinds of situations that arise regularly when managing GPOs in environments with mixed account types, non-domain infrastructure, or policies that interact with each other in unexpected ways.

The core takeaway from this lab:

Group Policy is a force multiplier: it can enforce consistent configurations across hundreds of machines with a single setting. But that same reach makes precision essential. Understanding GPO scope, security filtering, link placement, and the difference between Computer Configuration and User Configuration settings is what separates effective Group Policy administration from configurations that create more problems than they solve.
