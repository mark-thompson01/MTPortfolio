DNS Server Role Setup

Configuring DNS forwarders for external resolution and building out reverse lookup zones for every active VLAN on DC01.mtlab.local.

Domain: mtlab.local· Domain Controller: DC01.mtlab.local· OS: Windows Server 2022 Standard Evaluation

Overview

The DNS Server role was installed alongside Active Directory Domain Services during the original domain controller promotion. When a Windows Server is promoted to a domain controller, DNS is a required dependency: Active Directory uses DNS for everything from domain controller location to replication to service record registration. The role was already present and running on DC01 before any of the configuration steps covered here.

What was left to do was configure DNS to behave correctly for the lab environment. That meant three things: reviewing the existing forward lookup zone and its records, configuring forwarders so the DNS server could resolve external names, and creating reverse lookup zones for each active subnet.

Reviewing the Forward Lookup Zone

DNS Manager was opened from Server Manager via Tools. The initial view showed DNS > DC01 in the tree.

Expanding DC01 revealed the standard zone structure that Active Directory creates automatically during domain promotion:

  • Forward Lookup Zones
  • Reverse Lookup Zones (empty at this point)
  • Trust Points
  • Conditional Forwarders

Under Forward Lookup Zones, two zones were present: _msdcs.mtlab.local and mtlab.local. The _msdcs zone is an AD-integrated zone that holds service records for domain controller discovery. The mtlab.local zone is the primary forward lookup zone for the domain.

Clicking on mtlab.local showed the existing records: the Start of Authority (SOA) for dc01.mtlab.local, the Name Server (NS) record for dc01.mtlab.local, a Host (A) record for dc01 at 192.168.20.10 (static), and a Host (A) record for MTClient1 at 192.168.50.101. The MTClient1 record was a dynamically registered record from a prior lab session, confirming that domain-joined clients were registering themselves in DNS correctly.

Configuring DNS Forwarders

By default, a DNS server that cannot resolve a name from its own zones will attempt to use root hints to walk down the DNS hierarchy and find the authoritative server for the queried name. For a lab environment, it is simpler and faster to configure explicit forwarders: upstream DNS servers that handle external resolution.

To configure forwarders, DC01 was right-clicked in the DNS Manager tree and Properties was selected.

The Properties dialog opened on the Forwarders tab with an empty list. Clicking Edit opened the Edit Forwarders dialog, where two forwarder addresses were added:

  • 8.8.8.8 (Google Public DNS)
  • 1.1.1.1 (Cloudflare DNS)

Both entries showed "Attempting to resolve... Validating..." while the server attempted to verify connectivity to the forwarders. This is expected behavior at configuration time.

After clicking OK and returning to the Forwarders tab, both addresses were listed with "Attempting to resolve..." shown in the Server FQDN column, which resolves once the server successfully contacts them. With forwarders configured, DNS queries for names outside the mtlab.local zone would be forwarded to 8.8.8.8 and 1.1.1.1 rather than relying on root hints. External resolution from domain-joined lab machines would now work correctly.

Creating Reverse Lookup Zones

Forward lookup zones resolve names to IP addresses. Reverse lookup zones do the opposite: they resolve IP addresses back to names. Reverse DNS is used by many tools and services for logging, authentication, and verification. In an Active Directory environment, having reverse lookup zones configured for your subnets is considered good practice, and some services rely on it for proper operation.

Three reverse lookup zones were created, one for each active VLAN subnet:

  • 192.168.10.0/24 (VLAN 10 Servers): 10.168.192.in-addr.arpa
  • 192.168.20.0/24 (VLAN 20 Infrastructure): 20.168.192.in-addr.arpa
  • 192.168.40.0/24 (VLAN 40 Clients): 40.168.192.in-addr.arpa

Each zone was created using the New Zone Wizard, launched by right-clicking Reverse Lookup Zones in the DNS Manager tree and selecting New Zone. The same wizard settings were used for all three zones:

Settings applied to all three zones — Primary zone with "Store the zone in Active Directory" checked; replication scope set to "To all DNS servers running on domain controllers in this domain: mtlab.local"; IPv4 Reverse Lookup Zone; and "Allow only secure dynamic updates," since nonsecure updates would let any client on the network register DNS records without authentication.

Zone 1 — VLAN 10 Servers (10.168.192.in-addr.arpa)

The wizard was launched from the Reverse Lookup Zones node, with Primary zone and Active Directory storage selected, followed by the replication scope and reverse lookup zone type.

Zone 2 — VLAN 20 Infrastructure (20.168.192.in-addr.arpa)

The same wizard flow was repeated for VLAN 20, with the first zone now visible and running in the background.

Zone 3 — VLAN 40 Clients (40.168.192.in-addr.arpa)

The final zone followed the same pattern, with the first two zones now visible and running.

Each zone was completed in sequence. After all three reverse lookup zones were created, the Reverse Lookup Zones folder in DNS Manager showed all three zones with their full in-addr.arpa names, each running as an Active Directory-Integrated Primary zone.

With the reverse lookup zones in place, DNS on DC01 was now configured to handle both forward name resolution for the mtlab.local domain, external forwarding for names outside the lab, and reverse resolution for all three active subnets.

Summary

The DNS configuration on DC01.mtlab.local followed the standard Active Directory pattern: the forward lookup zone and its records were created automatically during domain promotion, forwarders were added for external resolution, and reverse lookup zones were manually created for each subnet. Storing all zones as Active Directory-integrated zones ensures the DNS data replicates through the same replication topology as the rest of the domain, rather than requiring separate DNS zone transfer configuration.

The following was completed:

  • Reviewed the existing forward lookup zone (mtlab.local) and confirmed dynamic client registration
  • Configured forwarders (8.8.8.8, 1.1.1.1) for external name resolution
  • Created three Active Directory-integrated reverse lookup zones, one per active VLAN subnet
  • Confirmed all zones running with secure dynamic updates enforced

With DNS fully configured, the next piece of the lab's core infrastructure was DHCP: bringing IP address assignment for all three VLANs under DC01 and getting cross-VLAN leases working through an IP helper-address relay on the layer 3 switch.
