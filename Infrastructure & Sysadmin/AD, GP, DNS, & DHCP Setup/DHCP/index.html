DHCP Server Role Setup

Installing the DHCP Server role on DC01, building scopes for all three active VLANs, and solving cross-VLAN lease delivery with an IP helper-address relay.

Domain: mtlab.local· Domain Controller: DC01.mtlab.local· OS: Windows Server 2022 Standard Evaluation

Overview

With the core infrastructure of the lab in place — the FortiGate firewall, the Cisco managed switches, Hyper-V, and Active Directory — the next step was to bring DHCP under the domain controller. Without DHCP, clients cannot receive IP addresses automatically, and getting it right on a segmented VLAN environment required more than just clicking through wizards. It required understanding how DHCP broadcasts behave across layer 3 boundaries and configuring the switch infrastructure to relay them correctly.

This page covers three things:

1

Installing the DHCP Server role on DC01.mtlab.local

2

Creating IPv4 scopes for all three active VLANs

3

Configuring an IP helper-address relay so cross-VLAN DHCP actually works

Environment Context

The lab runs three active VLANs across the managed switch infrastructure:

VLAN 10 — Servers192.168.10.0/24 — server infrastructure, mostly statically assigned
VLAN 20 — Infrastructure192.168.20.0/24 — DC01 lives here at 192.168.20.10
VLAN 40 — Clients192.168.40.0/24 — client network, dynamic DHCP matters most here

DC01.mtlab.local is the only server in the lab running DHCP. It also runs DNS and Active Directory Domain Services — all three roles coexist on the same VM, a common configuration in small environments and MSP client sites. The Raspberry Pi 5 at 192.168.10.5 handles BIND9 DNS as a secondary DNS resource, which is why it shows up alongside 192.168.50.10 in the DHCP scope options below — an artifact of an iterative DNS configuration process documented honestly rather than cleaned up after the fact.

Prerequisite: Static IP on the Domain Controller

Before the DHCP role was installed, DC01 needed a static IP address. A DHCP server handing out addresses to clients can't rely on a dynamically assigned address itself — if the server's IP changed, every scope option pointing to it as a gateway or DNS server would become invalid.

The NIC on DC01 was configured with static settings through Network Connections in the Control Panel: IP address 192.168.20.10, subnet mask 255.255.255.0, default gateway 192.168.20.1, and preferred DNS server 127.0.0.1. The loopback address is standard practice for a domain controller running the DNS role — pointing the server at itself ensures it uses its own DNS service for internal domain queries rather than reaching out to an external resolver.

With the static IP set, the server was ready for the DHCP role installation.

DHCP Server Role Installation

The DHCP Server role was added through Server Manager on DC01.mtlab.local. At the time of installation, the server was already running three roles: AD DS, DNS, and File and Storage Services — the dashboard showed Roles: 3 in the server groups panel before the installation began.

Add Roles and Features Wizard

The Add Roles and Features Wizard was launched from Server Manager via Manage. The wizard walked through the standard installation flow, opening on the "Before You Begin" screen and confirming the prerequisites: administrator account password set, static IP configured, and current security updates installed.

"Role-based or feature-based installation" was selected — the standard choice for adding a role to the local machine rather than deploying a Virtual Desktop Infrastructure configuration.

The server pool showed DC01.mtlab.local running Microsoft Windows Server 2022 Standard Evaluation — one server, one target.

From the roles list, DHCP Server was selected. AD DS and DNS were already marked as Installed.

When DHCP Server was checked, the wizard immediately prompted to add the required management tools: Remote Server Administration Tools, Role Administration Tools, and DHCP Server Tools. "Add Features" was clicked to accept these dependencies.

The DHCP Server information page appeared before confirmation, noting two important points: the server should have at least one static IP address configured, and scope planning should be completed before installation. Both conditions were already met.

The confirmation screen listed the components to be installed. The option to restart the server automatically if required was initially left unchecked.

A second pass through the confirmation screen prompted whether to allow automatic restarts, and the answer was yes.

Installation began on DC01.mtlab.local, moving through feature installation.

The installation completed with the message "Configuration required. Installation succeeded on DC01.mtlab.local," along with a link to Complete DHCP configuration — the next step.

After closing the wizard, a notification appeared in the Server Manager banner: "Post-deployment Configuration: Configuration required for DHCP Server at DC01." The dashboard now showed Roles: 4.

DHCP Post-Install Configuration

Clicking "Complete DHCP configuration" launched the DHCP Post-Install Configuration Wizard. The Description page explained what the wizard would do: create the DHCP Administrators and DHCP Users security groups, and authorize the DHCP server in Active Directory. Active Directory environments require DHCP servers to be explicitly authorized before they can hand out leases — this prevents rogue DHCP servers from operating on the domain network.

The Authorization page prompted for credentials to authorize the DHCP server in AD DS. The current user credentials were used: LAB\MT.Admin — the privileged domain admin account used for administrative tasks in the lab, following the tiered administration model established during the Active Directory configuration.

The Summary page confirmed both tasks completed successfully: creating security groups, and authorizing the DHCP server. The wizard noted that the DHCP Server service should be restarted for the new security groups to take effect.

The DHCP console was then accessible from Server Manager under Tools, and the dashboard showed four roles: AD DS, DHCP, DNS, and File and Storage Services.

DHCP Scope Configuration

With the DHCP role installed and authorized, the next step was creating scopes for each VLAN. A scope defines the range of IP addresses the DHCP server can distribute on a given subnet, along with the options clients receive alongside their lease: the default gateway, DNS servers, lease duration, and any exclusions.

Three scopes were created, one for each active VLAN, each through the New Scope Wizard launched by right-clicking IPv4 under dc01.mtlab.local in the DHCP console and selecting New Scope.

VLAN 10 Scope: Servers (192.168.10.0/24)

The first scope created was for VLAN 10, the Servers subnet. Most devices on this VLAN are statically assigned: the Raspberry Pi DNS server at 192.168.10.5, TrueNAS at 192.168.10.10, and the Raspberry Pi 3 NAS at 192.168.10.20. Because of this, the scope was configured primarily to define the subnet parameters rather than to actively hand out many leases.

Start IP address 192.168.10.10, end IP address 192.168.10.254, subnet mask 255.255.255.0 (/24).

The exclusion range was set to cover 192.168.10.10 through 192.168.10.254 — the entire upper portion of the scope excluded from dynamic distribution. This effectively reserved the address space for static assignments while still defining the subnet parameters within the DHCP server. Only addresses .1 through .9 remained outside the exclusion, providing a small dynamic pool if needed.

Lease duration was set to 8 days, 0 hours, 0 minutes — appropriate for a stable server subnet where most devices are statically assigned.

Router (default gateway) 192.168.10.1, parent domain mtlab.local, and a single DNS server: 192.168.10.5 (RPI-DNS).

The scope was activated immediately upon completion.

After activation, the DHCP console showed Scope [192.168.10.0] VLAN10-Servers with a status of Active.

VLAN 20 Scope: Infrastructure (192.168.20.0/24)

The second scope was for VLAN 20, the Infrastructure VLAN — where DC01 itself lives at 192.168.20.10, along with the Hyper-V host at 192.168.20.11. Like VLAN 10, most devices on this subnet are statically assigned, but defining the scope ensures the DHCP server has the subnet fully documented and can serve any infrastructure devices that come online dynamically.

Start IP address 192.168.20.10, end IP address 192.168.20.254, subnet mask 255.255.255.0 (/24).

The exclusion step was visited but no exclusion range was added for this scope — the start field showed 192.168.20.1 prefilled but was not committed. Static address management on VLAN 20 would be handled by convention rather than exclusion.

Two DNS entries were configured here: 192.168.50.10 appeared as an existing entry in the list, and 192.168.10.5 (RPI-DNS) was added as the second.

The scope was activated immediately. The DHCP console then showed both VLAN10-Servers and VLAN20-Infrastructure as Active.

VLAN 40 Scope: Clients (192.168.40.0/24)

The third scope was for VLAN 40, the Clients VLAN — where dynamic DHCP assignment matters most. Client machines joining the lab network need to receive an IP address automatically, along with the correct gateway and DNS server information.

Start IP address 192.168.40.10, end IP address 192.168.40.254, subnet mask 255.255.255.0 (/24).

The exclusion step was visited with 192.168.40.1 prefilled in the start field. No exclusion range was committed, leaving the full 192.168.40.10 through 192.168.40.254 range available for dynamic distribution.

The same dual DNS configuration was applied as on VLAN 20: 192.168.50.10 and 192.168.10.5 (RPI-DNS).

The scope was activated immediately. After completion, the DHCP console showed all three scopes active.

Additional Configuration: Making Cross-VLAN DHCP Work

At this point, the DHCP server was installed, authorized, and had three active scopes. But there was a problem: a Windows client on VLAN 40 would not receive a DHCP lease.

The reason comes down to how DHCP works at a network level. DHCP discovery packets are broadcast traffic, and broadcast traffic does not cross layer 3 boundaries by default. In a segmented VLAN environment, a client on VLAN 40 sends a DHCPDISCOVER broadcast that never reaches the DHCP server sitting on VLAN 20, because the router or layer 3 switch between them drops broadcasts at the VLAN boundary.

The fix — an IP helper-address (DHCP relay): it tells the layer 3 device to intercept DHCP broadcasts on a given interface and forward them as unicast packets to a specified IP address — here, the DHCP server at 192.168.20.10. The DHCP server receives the forwarded request, determines which scope to respond from based on the originating subnet, and sends the lease back through the same path.

Configuring IP Helper-Address on Switch002

Switch002 is the Catalyst 3550, which functions as the layer 3 core of the lab — inter-VLAN routing runs through its VLAN SVIs (switched virtual interfaces). Since Switch002 is the routing point between VLANs, it's also the right place to configure the DHCP relay.

The configuration was applied via PuTTY on COM4, entering privileged exec mode and then global configuration mode:

Switch002>enable
Switch002#conf t
Switch002(config)#interface vlan 10
Switch002(config-if)#ip helper-address 192.168.20.10
Switch002(config-if)#exit
Switch002(config)#interface vlan 20
Switch002(config-if)#ip helper-address 192.168.20.10
Switch002(config-if)#exit
Switch002(config)#interface vlan 40
Switch002(config-if)#ip helper-address 192.168.20.10
Switch002(config-if)#exit
Switch002(config)#end
Switch002#write memory
Building configuration... [OK]

The ip helper-address command was applied to all three VLAN SVIs, each pointing to 192.168.20.10 — the static IP of DC01. The configuration was saved with write memory.

With the relay in place, DHCP broadcasts from clients on VLANs 10, 20, and 40 were now forwarded to the DHCP server as unicast packets. DC01 could receive the requests, identify which scope to respond from based on the originating subnet, and issue leases correctly. Cross-VLAN DHCP was working.

Summary

The ip helper-address configuration on Switch002 was the piece that made the DHCP deployment actually functional. Installing the role and creating scopes is straightforward — getting DHCP to work across VLANs requires understanding how broadcast traffic behaves at layer 3 boundaries and configuring the relay correctly on the right device. In this lab, that meant Switch002, the Catalyst 3550 handling inter-VLAN routing, needed the relay configured on all three VLAN SVIs before clients on those VLANs could receive leases.

The following was completed:

  • Configured a static IP on DC01 as a prerequisite for the DHCP role
  • Installed the DHCP Server role and completed post-install authorization in Active Directory
  • Created three IPv4 scopes — VLAN10-Servers, VLAN20-Infrastructure, VLAN40-Clients — each with appropriate exclusions and lease durations
  • Diagnosed the cross-VLAN broadcast problem and configured an IP helper-address relay on all three VLAN SVIs on Switch002

With DHCP and DNS both operational, the lab network is now fully functional as a domain environment: clients on any VLAN can receive IP addresses automatically, resolve both internal and external names, and communicate across the segmented network through the layer 3 infrastructure established on the managed switches.
