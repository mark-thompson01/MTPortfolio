Security Hardening Pass — MTPortfolio Infrastructure & Security

FortiGate 60E Security Configuration

This page covers the security hardening pass performed on the FortiGate 60E firewall, building on the initial deployment and connectivity work documented in the Infrastructure & Sysadmin section. Where that earlier work focused on getting traffic to flow correctly (interfaces, routing, baseline policies), this section focuses on defending the device and the network behind it: administrative access control, firewall policy discipline, DoS protection, certificate management, SSL inspection, VPN access, and logging.

Before any of that, one thing needs to be stated plainly, because it shapes every decision documented below.

Constraint

This FortiGate 60E does not have an active FortiCare subscription. As a result, firmware updates are blocked, and several UTM-dependent security features (IPS, Antivirus, Web Filtering, Application Control) are unavailable without a paid license. The hardware has also reached end-of-life as a widely deployed model. Rather than pay for a subscription on EOL hardware whose value here is portfolio and learning, not production uptime, the approach taken throughout this section was to harden everything genuinely available without a license, and document the licensing wall honestly where it applies. See the Licensing & EOL Constraints section at the end of this page for the full reasoning.

Jump Host Prerequisite: Administrative Access Setup

FortiGate administrative access in this environment is restricted to trusted hosts (covered in the next section). Before that restriction could be configured, a dedicated administrative access point was needed. The choice of that access point, and the network path required to reach it, surfaced several real configuration issues worth documenting in detail.

Choosing the Access Point

The first instinct was to browse to the FortiGate directly from DC01, the domain controller, since it was the only always-on Windows machine readily available. On reflection, this was reconsidered: DC01 is the highest-value asset in the lab, holding every domain identity, and routinely using it as a general-purpose admin workstation for browsing to other infrastructure increases its exposure for no real benefit. A browser is one of the more common footholds for compromise, and standard practice is a dedicated admin or jump workstation separate from identity infrastructure.

The existing Win11-Client VM (MTCLIENT1) was repurposed for this role instead: moved onto the Management VLAN (VLAN 50), given a static IP, and used going forward as the standing jump host for FortiGate, switch, and other infrastructure administration.

Design Decision

Network segmentation (which VLAN a device sits on) and credential tiering (which account logs into that device) are separate controls. Placing the jump host on the Management VLAN does not, by itself, make it safe to log into with a domain admin account. The Windows OS login on the jump host uses SOperations, a dedicated security-operations account, kept separate from MT.Admin. This avoids caching domain admin credentials on a workstation used for routine browsing and administrative tasks.

Worth being precise about the limits of this choice: SOperations is a domain account, not a local account scoped to this VM alone. Logging into Windows interactively with any domain account, even a lower-privilege one, still caches a domain-valid credential on that machine. If the jump host were ever compromised, whatever SOperations has rights to elsewhere in the domain becomes reachable, not just this VM. This is meaningfully better than using MT.Admin, since SOperations carries far less privilege than domain admin, but it is not equivalent to a genuinely local account that has no value outside this single machine. A dedicated local account would be the stricter isolation choice for a pure jump host; SOperations was used here as a reasonable middle ground, since it already existed as a scoped security-operations account and matched the credential-tiering pattern established elsewhere in this lab.

Static IP and VLAN Tagging

The Win11-Client VM was assigned a static IP of 192.168.50.20/24, gateway 192.168.50.6 (the Management VLAN SVI on Switch002), with DC01 (192.168.20.10) set as the primary DNS server so the VM could authenticate to the domain. Static addressing was used deliberately, consistent with every other administrative or infrastructure device in the lab: management-plane devices should have predictable addresses, not DHCP leases that can change.

On the Hyper-V side, the VM's virtual network adapter was tagged with VLAN ID 50 in the adapter's settings, so its traffic would be correctly tagged as it left the host through the external virtual switch.

Discovering the Fa0/2 Access-Mode Misconfiguration

With the VM tagged and addressed, it still could not reach its gateway. Systematic troubleshooting (confirming the VM's own configuration, checking ARP, checking the VLAN 50 SVI on Switch002, and finally checking the MAC address table on Switch001) traced the problem back to Switch001 Fa0/2, the port connecting SRV-HYPERV-01 to the switch stack.

This was a real misconfiguration, not a new problem introduced by this work: Fa0/2 was set to access mode with a single VLAN (20) assigned, despite already needing to carry traffic for a Hyper-V host running VMs across multiple VLANs (10, 20, 40, and now 50). An access port can carry exactly one VLAN; trunk-allowed-VLAN and native-VLAN lines were present in the configuration but completely inert, since access mode ignores them entirely.

A first attempt to fix this by simply adding VLAN 50 to the trunk-allowed list did not resolve the issue, since the port was still in access mode:

Removing Port Security and Converting to Trunk Mode

Correcting this required two changes: converting Fa0/2 to trunk mode, and removing port security entirely. Port security is designed for edge or access ports defending against unauthorized device connections in physically accessible spaces; it is a poor fit for a shared hypervisor uplink, where the number of MAC addresses is inherently unpredictable as VMs are added, rebuilt, or migrated over time. A fixed MAC limit on this kind of port creates operational friction without addressing a realistic threat, since the actual trust boundary here is the physical security of the server room and the hypervisor host itself.

Verifying the Fix

One additional, harder-to-spot issue remained after the trunk conversion: the VM could intermittently reach its gateway, then lose connectivity entirely, even with the switch-side configuration correct. This traced back to the VM's Hyper-V network adapter itself: the VLAN identification checkbox had reverted to unchecked at some point during the VM's reboot cycles, causing its traffic to leave untagged and fall through to the trunk's native VLAN (99) instead of VLAN 50. Re-enabling VLAN tagging on the adapter resolved this immediately.

Lesson Learned

Two distinct failure modes can produce the identical symptom of an unreachable gateway on a trunked VLAN: the VLAN being blocked (not in the trunk's allowed list) and the VLAN never being applied in the first place (untagged traffic silently falling to the native VLAN). Both look the same from a simple ping test. Confirming where a device's traffic actually lands, via the switch's MAC address table, is a more reliable diagnostic step than testing connectivity alone.

This finding was also fed back into the Managed Switch Security documentation as a short addendum, since that document's original coverage of Fa0/2 predated this correction.

Administrative Access Hardening

With the jump host in place and reachable, the FortiGate's administrative access itself was hardened: restricting which hosts can reach the admin interface, disabling unencrypted access, tightening session and lockout behavior, enforcing a real password policy, and replacing the default admin account.

Trusted Hosts

Administrative access was restricted to the jump host's IP address specifically (192.168.50.20/32), rather than the broader Management VLAN subnet. This is a deliberate defense-in-depth choice: even though VLAN 50 is itself a restricted segment, scoping trust to a single host means that if another device ever ends up on that VLAN, misconfigured or otherwise, it still cannot reach the FortiGate admin interface without being explicitly added.

Access Protocols and DHCP Cleanup

Reviewing the internal interface's administrative access settings surfaced two items worth correcting: HTTP was still enabled alongside HTTPS, and a DHCP server was enabled on the interface serving an address range (192.168.1.110-192.168.1.210) that does not correspond to the interface's actual subnet (192.168.100.0/30, a four-address transit link to Switch002). This DHCP server could never actually hand out a usable address on this interface; it was a stale default left over from initial setup.

Note

HTTP access was disabled without incident since the active session was already using HTTPS. Disabling HTTP does not require a trusted TLS certificate; a self-signed certificate (even the FortiGate's factory default) still provides working, encrypted HTTPS, it is simply not trusted by the browser by default. Certificate replacement is covered separately in the Certificate Management section.

Idle Timeout and Password Policy

Admin idle timeout was reduced from the default to 5 minutes. A password policy was configured requiring a 12-character minimum. An initial pass at enforcing character complexity did not fully apply as intended; this was caught during a screenshot review and corrected to properly enforce upper case, lower case, numeric, and special character requirements, with password reuse disabled.

Admin Account Replacement

The default admin account name is well known on any FortiGate deployment, making it a predictable target. A named replacement account (SOperations) was created with an equivalent super_admin profile and the same trusted-host restriction, and the original admin account was locked down rather than deleted, since some firmware versions restrict deleting the last super_admin account. Its trusted host was set to an unreachable value (0.0.0.0/32), rendering it effectively unusable without being reachable from anywhere on the network.

Firewall Policy Hardening Pass

The FortiGate's implicit deny is enabled by default and does not require explicit configuration to function; anything not explicitly permitted is already dropped. However, the implicit deny does not log by default, making it invisible in day-to-day operation and impossible to point to as evidence of a working default-deny posture. This pass adds an explicit, logged deny-all policy for every interface pairing already in use, sitting below the existing legitimate allow rules.

Explicit Deny-All Policies

An explicit deny-all policy was added for each interface pairing already carrying traffic: internal to internal, internal to wan1, and wan1 to internal. Each was configured with source ALL, destination ALL, service ALL, action DENY, and logging enabled, then positioned below the corresponding allow rule for that pairing. The FortiGate GUI's Incoming Interface field only accepted a single interface at a time rather than a blanket 'any' option on this firmware, so each pairing was created as its own explicit policy via the CLI.

Lesson Learned

A duplicate deny-all policy on the internal-to-wan1 pairing was discovered during review (two policies, both matching the same interface pair with identical settings). Since FortiGate evaluates policies top to bottom and stops at the first match, the duplicate was functionally harmless but confirmed via the CLI's raw config output (srcintf and dstintf values) rather than the GUI's interface-pair grouping, which can be easy to misread. The redundant policy was deleted, leaving one explicit deny-all per interface pairing.

DoS Protection Policies

DoS Policy is a core FortiOS feature that does not require a FortiGuard subscription, but it is hidden from the GUI navigation by default on this firmware. It was enabled through Feature Visibility before it could be configured.

Anomaly Sensor Configuration

A DoS protection policy was applied to the WAN1 interface, the internet-facing side of the firewall, where flood and scan attempts would first arrive. Anomaly sensors were enabled across Layer 3 (session-count based) and Layer 4 (protocol-specific flood and scan) categories, each set to Block with logging enabled, using FortiGate's suggested default thresholds rather than hand-tuned values, since no observed traffic baseline exists yet for this lab to tune against.

Certificate Management

The FortiGate ships with a self-signed factory default certificate (Fortinet_Factory) for admin GUI access. Replacing it with a device-specific certificate is legitimate hardening that requires no license, but current FortiOS firmware only exposes a Certificate Signing Request (CSR) workflow in both the GUI and CLI, meaning a certificate cannot be self-signed and completed on the device alone without an external certificate authority to sign the request.

Constraint

Attempting to generate a certificate directly, both through the GUI (Generate CSR is the only generation option present) and through the CLI (execute vpn certificate local generate, which is documented as producing a CSR as well, despite living under the vpn certificate command namespace for historical reasons), confirmed that current FortiOS firmware does not offer a one-step self-signed local certificate option the way older versions did.

The workaround: a self-signed certificate and private key were generated externally using PowerShell's New-SelfSignedCertificate, exported as a password-protected PKCS #12 (.pfx) file, and imported into the FortiGate directly as a complete local certificate, bypassing the CSR flow entirely.

The new certificate was then applied as the HTTPS server certificate for administrative access, replacing the factory default.

Note

The certificate is consistently named FTG60E-Admin-Cert (transposed letters) rather than FGT60E-Admin-Cert throughout the PowerShell commands, the PFX filename, and the FortiGate import, a naming typo carried through consistently rather than corrected mid-stream. It is functionally harmless and left as-is, in keeping with documenting the process as it actually happened rather than a cleaned-up version.

SSL Inspection (Certificate-Inspection Mode)

Full SSL deep-inspection, which decrypts, scans, and re-encrypts traffic, depends on the UTM engine and is not available without a FortiGuard subscription. Certificate-inspection mode is a lighter alternative available without a license: it examines the server certificate and SNI (Server Name Indication) during the TLS handshake without decrypting the payload, and can flag or block based on certificate validity, without providing content-level scanning.

The built-in certificate-inspection profile was reviewed and applied to the LAN-to-WAN policy, with server certificate validation set to block expired, revoked, and validation-failed certificates.

Verifying the Profile Is Active

An initial verification attempt (browsing to a known-bad certificate test site and expecting a corresponding FortiGate log entry) surfaced two separate issues rather than confirming success: Forward Traffic logs were empty entirely, and the policy's own Log Allowed Traffic setting was found set to Security Events only rather than All Sessions.

Lesson Learned

A browser's own certificate warning (Chrome's 'Your connection is not private') is generated entirely client-side and proves nothing about whether a firewall in the traffic path is inspecting anything. Confirming SSL inspection is actually functioning requires checking the FortiGate's own logs for the session and confirming the SSL Inspection Profile field is populated, not just observing that the browser flagged the certificate.

Correcting the policy's logging setting to All Sessions, and separately confirming logtraffic all was actually saved in the running configuration (an earlier GUI change had not persisted), resolved both issues. With logging correctly capturing all sessions, the badssl.com test session and a normal HTTPS session both appeared in Forward Traffic, confirming the certificate-inspection profile was actively evaluating traffic in both directions.

VPN

SSL-VPN is a core, unlicensed FortiGate feature, and was configured to provide remote administrative access to the lab's Management VLAN. Like DoS Policy, SSL-VPN's GUI presence required enabling first.

Local VPN User and Group

VPN authentication for this pass uses a local FortiGate user rather than a domain account. A local user (vpn.mark) and a corresponding user group (SSLVPN-User) were created to scope VPN access.

Destination Scope and Policy

A firewall address object was created for the Management VLAN subnet, used as the VPN policy's destination, and a firewall policy was created connecting the SSL-VPN tunnel interface to the internal interface, permitting SSLVPN-User group members to reach the Management VLAN.

Correcting Scope and NAT

Two settings on the initial policy were tightened after review. NAT was disabled: with NAT enabled, VPN client traffic reaching internal resources would have been source-translated to the FortiGate's own internal address, obscuring which VPN session actually generated any given connection in downstream logs. Service was narrowed from ALL to HTTPS and SSH specifically, matching the intended administrative use case rather than leaving the policy open to any protocol.

Split tunneling was configured on the SSL-VPN portal using the 'Enable split tunneling, based on policy destination' option, which automatically derives the routed subnet from the firewall policy's destination object rather than requiring a separately maintained routing address list. Full tunnel was deliberately not used: its primary justification is centralized traffic inspection through UTM security profiles, which this device does not have licensed, so routing all client traffic through the tunnel would add overhead without the corresponding benefit.

Local Logging

Log & Report settings on this FortiGate 60E expose only a Memory logging toggle, with no Disk logging tab available in the GUI. This is consistent with the model's hardware: entry-level FortiGate appliances without an SD card installed typically have no onboard storage for persistent logs, meaning logging here is memory-based only and does not survive a reboot.

Constraint

Logging on this device is memory-resident only. This is treated as a documented hardware constraint consistent with the device's broader licensing and lifecycle limitations, not a misconfiguration. A production deployment needing persistent, reboot-surviving logs would require either an SD card (if supported on this model) or forwarding to an external log receiver such as FortiAnalyzer or syslog, neither of which is present in this lab.

Verifying Logs Actually Populate

With the LAN-to-WAN policy's Log Allowed Traffic setting corrected to All Sessions, and logtraffic all confirmed saved in the running configuration, Forward Traffic logging was retested end to end: fresh HTTPS traffic was generated from the jump host, and the resulting sessions were confirmed appearing in Forward Traffic with source, destination, and application detail populated.

Lesson Learned

Forward Traffic logs were empty for an extended period during SSL inspection verification, which was initially assumed to be an SSL inspection problem. The actual cause was the policy's own logging scope (Security Events only, not All Sessions), unrelated to SSL inspection at all. When a verification step produces no data at all, checking whether logging itself is correctly scoped is a useful early diagnostic step, before concluding the feature under test is not working.

Licensing & EOL Constraints

This FortiGate 60E does not have an active FortiCare or UTM subscription, and the hardware has reached end-of-life as a widely deployed entry-level model. These two facts shape what this page does and does not cover, and are worth stating plainly rather than working around silently.

What Requires a License

  • Firmware updates. Current FortiOS versions actively check license status before allowing an upgrade to proceed; device registration itself is free, but the upgrade is gated behind at least a base FortiCare support contract.
  • IPS (Intrusion Prevention), Antivirus, Web Filtering, and Application Control, all of which depend on the UTM engine and FortiGuard content updates.
  • Full SSL deep-inspection with content scanning, as distinct from the certificate-inspection mode used in this document, which does not require a license.

What Does Not Require a License

Everything documented on this page was configured without any paid subscription: administrative access hardening, firewall policy discipline and explicit deny-all logging, DoS protection policies, local certificate management, certificate-inspection SSL mode, SSL-VPN with local authentication, and memory-based local logging. Taken together, this represents a genuinely complete hardening pass within the constraints of the hardware, not a partial one.

Why Paying for a License Was Not Pursued

Given that the FortiGate 60E is already end-of-life, a paid FortiCare or UTM subscription would unlock features on hardware that Fortinet has otherwise stopped supporting with security patches and updates once its lifecycle window closes. For a home lab whose purpose is demonstrable, hands-on portfolio work rather than production uptime, that expense does not provide proportionate value. Understanding and clearly articulating a vendor's licensing and lifecycle model, including which features are gated behind which subscription tier, and making a deliberate, cost-aware decision not to pursue that path, is itself a legitimate piece of operational judgment.

Compensating Network Design

The absence of licensed threat-inspection features is partially offset by the network's layered design. The FortiGate sits behind the SOHO router's own NAT boundary with no inbound port forwarding, meaning it is not directly reachable from the internet; opportunistic scanning and exploit attempts targeting known FortiGate CVEs cannot reach it from outside. The SOHO router's own LAN segment and the lab's internal VLANs are also separate broadcast domains, so a device on the SOHO segment has no Layer 2 visibility into the lab's VLANs without an explicit FortiGate policy permitting it.

This does not eliminate risk. It does not protect against lateral movement originating from an already-compromised device inside the lab's own VLANs, which is precisely why the administrative-access trusted-host restrictions and local-in policy scoping documented on this page matter as a compensating control, not the network segmentation alone. Reduced attack surface from unsolicited external traffic, combined with deliberate internal access controls, is the accurate way to describe this device's security posture; it is not accurate to describe it as invulnerable.
