SPAN - Switch Port Analyzer Configuration

Mirroring live switch traffic to a dedicated capture VM using a Cisco SPAN session, an isolated Hyper-V virtual switch, and Wireshark — to get real visibility into what's actually crossing the wire in the lab.

1Objective

Port mirroring (SPAN — Switch Port Analyzer) copies traffic from one or more source ports to a destination port, so a packet analyzer can see traffic it would never normally receive on a switched network. The goal here was to mirror the uplinks and trunk carrying inter-VLAN and lab traffic to a capture point, then use Wireshark to baseline normal traffic and spot anything worth investigating — retransmissions, failed auth, unexpected broadcast/multicast chatter, DNS failures, and so on.

The setup has two halves: configuring the SPAN session on the physical Cisco switch, and building an isolated capture path on the Hyper-V host so a VM's NIC receives that mirrored traffic without ever touching the routed lab network.

2Configuring the SPAN Session on the Switch

On the Cisco switch, a local SPAN session was created with multiple source ports feeding a single destination port dedicated to monitoring:

Switch001#conf t
Switch001(config)#monitor session 1 source interface fa0/2 both
Switch001(config)#monitor session 1 source interface fa0/3 both
Switch001(config)#monitor session 1 source interface fa0/4 both
Switch001(config)#monitor session 1 source interface fa0/5 both
Switch001(config)#monitor session 1 source interface fa0/23 both
Switch001(config)#monitor session 1 destination interface fa0/6
Switch001(config)#end
Switch001#write memory

Fa0/2–Fa0/5 and the Fa0/23 trunk were set as sources in both directions (RX and TX), with Fa0/6 as the dedicated destination port feeding the capture NIC. show monitor session 1 confirms the session is active with ingress learning disabled on the destination port, which is expected — a SPAN destination port doesn't participate in normal switching.

3Building an Isolated Capture Path in Hyper-V

Rather than feeding mirrored traffic into an existing lab switch, a second physical NIC on the Hyper-V host (a USB-to-Gigabit adapter) was cabled directly to the SPAN destination port and dedicated entirely to capture traffic. This keeps mirrored traffic off the routed lab network and avoids any risk of loops or duplicate frames reaching production VMs.

Creating a dedicated external virtual switch

In Hyper-V Manager, a new external virtual switch was created and bound to that dedicated adapter.

Attaching the capture VM

A Windows 11 client VM was given a second network adapter connected to the SPAN-Monitor switch, dedicated purely to receiving mirrored traffic.

Setting the NIC to port-mirroring destination

Under the new adapter's Advanced Features, the mirroring mode was set to Destination — this is the setting that actually tells Hyper-V to hand this adapter a copy of traffic rather than treat it as a normal network connection.

Why a second NIC and a dedicated vSwitch instead of just plugging Wireshark into the trunk: isolating the mirrored feed on its own virtual switch and physical adapter means the capture VM never sees — or injects into — live lab traffic. It's a passive tap in spirit, built out of what was on hand rather than a purpose-built TAP device.

Confirming the physical adapter mapping

A quick check in Network Connections on the host confirms Ethernet 3 is the ASIX USB-to-Gigabit adapter carrying the SPAN feed — the same adapter bound to the SPAN-Monitor virtual switch above.

4Capturing Traffic with Wireshark

With the capture path in place, Wireshark was pointed at Ethernet 3 inside the capture VM to start pulling in the mirrored traffic.

First look: unfiltered capture

An unfiltered capture immediately showed a healthy amount of Layer 2 control-plane noise mixed in with real traffic — PVST+ BPDUs advertising the STP root bridge, ARP requests, and ICMP echo traffic between lab hosts.

Cutting the noise: filtering out STP and ARP

Since Fa0/23 (the inter-switch trunk) was one of the mirrored sources, STP BPDUs and ARP broadcasts dominated the capture. A simple display filter cleared that out and left the traffic actually worth reading:

not stp and not arp

5Protocol-Level Analysis

With a clean feed established, protocol-specific filters were used to dig into what individual hosts were actually doing.

ICMP

Filtering on icmp surfaced steady echo request/reply pairs between 192.168.20.10 and 192.168.10.20, plus a Destination Unreachable (Port Unreachable) response from 192.168.10.5 — a clear sign that host was rejecting traffic on a closed port rather than silently dropping it.

DNS

Filtering on dns showed repeated queries for 1.debian.pool.ntp.org and 0.freebsd.pool.ntp.org returning Server failure responses from the internal resolver at 192.168.10.5 — a useful flag that NTP resolution wasn't fully healthy for at least one lab host.

SMB / SMB2

Filtering on smb caught NetBIOS Host Announcements naming DC01 as a Domain Controller. Filtering on smb2 traced a full negotiate-and-authenticate exchange ending in STATUS_LOGON_FAILURE for a service account — worth following up as a possible stale credential or misconfigured account.

6Takeaways

  • SPAN plus an isolated capture VM gives real visibility into switched traffic without touching production VLANs or risking a loop on the destination port.
  • Mirroring a trunk means STP and ARP will dominate the raw capture — not stp and not arp is the fastest way back to signal.
  • Protocol-specific filters (icmp, dns, smb2) turned up concrete, actionable findings: a port-unreachable host, unhealthy NTP resolution, and a failing service account logon — exactly the kind of thing packet analysis is for.
